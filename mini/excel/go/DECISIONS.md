# Решения

Формат: вопрос → решение → почему.

## Данные и очистка

1. **Как отличать дату Excel от текста, если excelize отдаёт строки?**
   → Читаю ячейки как «сырые» значения (`RawCellValue: true`): дата Excel приходит
   серийным номером (`"45668"`). Если значение парсится как число — это серийный номер
   (эпоха 1899-12-30, допустимый диапазон 61…2958465, дробная часть-время отбрасывается);
   иначе — строгий `DD.MM.YYYY` через `time.Parse("02.01.2006")`.
   → Так обрабатываются оба формата из ТЗ, а невозможные даты (`31.02.2025`) отсекаются.
   Число, сохранённое как текст, тоже считается серийным номером — на этих данных такого нет.

2. **Порядок проверок и «первое вхождение» дубликата.**
   → Сначала пропуск пустых строк, затем проверка дубля по `order_id` (с обрезкой
   пробелов), и только потом валидация полей. Первое вхождение регистрируется до валидации.
   → Прямо следует из правила 2: первое вхождение «обрабатывается, даже если невалидно»,
   значит последующие копии — дубликаты независимо от его судьбы.

3. **Одна причина на строку?** → Да, первая сработавшая (id → дата → количество →
   цена → скидка → обязательные текстовые поля). → Строка считается пропущенной один раз;
   этого достаточно для лога.

4. **`quantity` вида `"2.0"` / `2.5`.** → `2.0` принимается как 2, `2.5` — пропуск.
   → Excel хранит все числа как float; «целое» проверяю по значению.

5. **`unit_price` с пробелами-разделителями тысяч (`"1 234,50"`)** → принимается;
   одновременно `.` и `,` (`"1.234,50"`) — пропуск как неоднозначное.
   → Безопаснее отвергнуть, чем угадать порядок разделителей.

6. **`discount` вне [0, 1] (`1.5`, `150%`, `-0.1`) или текст** → строка пропускается
   (`invalid_discount`). → В ТЗ указано «доля от 0 до 1»; скидка > 100 % дала бы
   отрицательную выручку. В исходных данных таких значений нет.

7. **Пустые `order_id`, `region`, `category`, `product` (при непустой строке).**
   → Пропуск с отдельной причиной. → Без них строку нельзя корректно агрегировать
   (или проверить на дубль). В исходных данных таких строк нет, на результат не влияет.
   `manager` не обязателен — он не участвует в агрегатах.

8. **Колонки ищутся по заголовку, а не по позиции** (без учёта регистра и пробелов);
   нет нужной колонки — понятная ошибка со списком недостающих. Короткие строки
   (нет последних ячеек) дополняются пустыми значениями → пустая скидка = 0.

9. **Лист `Targets` — строгий:** любая битая строка плана (не `YYYY-MM`, нечисловой
   или отрицательный `target`) — ошибка с номерами строк, утилита завершается с кодом 1.
   → Молча выброшенная строка плана исказила бы `plan_vs_fact`; правила очистки в ТЗ
   относятся только к `Sales`. Регион в плане тоже обрезается.

## Агрегаты и формат вывода

10. **«Полная точность» суммирования.** → `float64` + компенсированное суммирование
    Ноймайера; округление до 2 знаков (`math.Round(x*100)/100`) только при сериализации.
    → Даёт точность на уровне double без внешних decimal-библиотек (тест: десять раз 0.1 = 1).

11. **Формат чисел в JSON.** → Все денежные значения и `completion_pct` пишутся с ровно
    двумя знаками (`207149040.50`, `0.00`) через тип `Money` с `MarshalJSON`.
    → Это валидные JSON-числа, а в выводе явно видно, что значение — float (как `0.0` в ТЗ).
    Целые счётчики (`valid_rows`, `quantity`) — целые.

12. **`plan_vs_fact`: какие регионы и что такое «за год».** → Объединение регионов
    из фактов и плана, сортировка по алфавиту; `fact` = вся выручка региона,
    `target` = сумма всех месяцев плана. Если плана нет — `target = 0` и
    `completion_pct = 0` (а не деление на ноль / `null`).
    → В данных ровно один год (2025), фильтровать по году не нужно; схема в ТЗ требует число.

13. **Сортировка «по алфавиту» / ключей.** → Побайтовое сравнение UTF-8 строк
    (= порядок кодовых точек Unicode), как у `json.dumps(sort_keys=True)` в Python.
    → Для кириллицы совпадает с алфавитом (кроме «ё», которой нет в данных) и
    детерминирован без локалей.

14. **`top_products`: при равенстве выручки — по названию по возрастанию;**
    `quantity` — сумма количества товара по всем валидным строкам.

## Графики и отчёт

15. **Библиотека графиков** → `gonum.org/v1/plot` (самая популярная чистая Go-библиотека,
    без CGO). Кругового графика в ней нет — кольцевая диаграмма нарисована своим
    `plot.Plotter` (сектора полигонами, легенда с долями и суммами справа).
16. **Шрифт** → Liberation Sans из комплекта gonum/plot (есть кириллица; не зависит от
    системных шрифтов). Задаётся через `plot.DefaultFont` в `init()` пакета `charts` —
    другого способа сменить гарнитуру по умолчанию в gonum/plot нет.
17. **Разделители тысяч** → пробел (русская норма): оси «20 000 000», подписи значений
    «17,5 млн», в HTML «207 149 040,50 ₽». На PNG вместо «₽» пишу «руб.» — не во всех
    шрифтах есть глиф рубля.
18. **report.html** → самодостаточный файл: PNG встроены как `data:` URI, чтобы страницу
    можно было переслать одним файлом. PNG при этом остаются отдельными файлами.
19. **Лог пропусков** → `out/skipped.csv` (всегда) + сводка в stderr; построчный лог в
    stderr — по флагу `-v`, чтобы 200 строк не засоряли вывод по умолчанию.
20. **Пустые данные** → вместо паники gonum/plot (`NominalX` без значений) рисуется
    заглушка «Нет данных».

## Инструменты

    `go 1.27.3`; пересобранный 2.12.2 падает на export data Go 1.27. → Использую
    golangci-lint **v2.15.0**, собранный текущим Go (`make lint` делает `go run …@v2.15.0`),
    конфиг `.golangci.yml`: стандартный набор + errorlint, gocritic, gosec, misspell,
    revive, unparam и др., форматтеры gofmt/goimports.
