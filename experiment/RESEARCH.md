# Ресерч: Python vs Go для AI-агентов (публичные источники, 18.11.2026)


### За Python (агенту проще)
1. **Больше обучающих данных.** The Stack v1, permissive, near-dedup: Python 80,4 ГБ / 15,0 млн файлов против Go 34,9 ГБ / 6,2 млн, то есть в 2,3 раза больше. В The Stack v2 dedup: Python 233 ГБ против Go 55 ГБ, в 4,3 раза больше. [arXiv 2211.15533](https://arxiv.org/html/2211.15533v1), [arXiv 2402.19173](https://arxiv.org/html/2402.19173v1)
2. **Агенты чаще решают реальные задачи на Python.**
   - Multi-SWE-bench (ByteDance, NeurIPS 2025): «высокоуровневые Python/Java обгоняют системные Go/Rust». Итог из слайдов NeurIPS: «Python? Solid. C/Rust/Go? Still a nightmare». [arXiv 2504.02605](https://arxiv.org/abs/2504.02605), [слайды](https://neurips.cc/media/neurips-2025/Slides/121692.pdf)
   - SWE-bench Multilingual: на Go решено 13/42 (31%). Авторы: «LLM более уверенно работают с Python». [swebench.com](https://www.swebench.com/multilingual.html)
   - Исключение — SWE-Bench Pro (Scale AI): там Go и Python в лидерах. [arXiv 2509.16941](https://arxiv.org/abs/2509.16941)
3. **Меньше токенов на решение.**
   - Tokenmaxxing (Northeastern, SPLASH 2026): низкоресурсные языки стоят заметно дороже Python при той же доле успешных решений. Агент на Python почти всегда пишет правильное решение с первой попытки. Go в исследовании не было. [arXiv 2607.22807](https://arxiv.org/abs/2607.22807)
   - Эксперимент с Claude Code (36 реализаций): Python выиграл по токенам в 6 из 12 задач, Go — в 3. Разброс внутри одного языка (3–14×) больше, чем разница между языками (20–40%). [GitHub vikas-t/llms-token-perf](https://github.com/vikas-t/llms-token-perf)
4. **Бенчмарки исторически строились на Python.** HumanEval, MBPP и SWE-bench изначально только на Python, и методы агентов оптимизированы под него. Это прямо указано как одна из причин разрыва в Multi-SWE-bench. [MultiPL-E arXiv 2208.08227](https://arxiv.org/abs/2208.08227)
5. **Лаконичность.** Нет `if err != nil`, меньше шаблонного кода, плотнее токенизация. Это мнение, а не исследование (Medium, Towards AI).

### Против Python (где Go сильнее)
1. **Типы ловят основной класс ошибок LLM.** 94% ошибок компиляции в сгенерированном LLM коде — провалы проверки типов (исследование PLDI 2025 на TypeScript). В Python такие ошибки всплывают только при выполнении. [arXiv 2504.09246](https://arxiv.org/abs/2504.09246)
2. **Индустрия уходит к типизированным языкам.** GitHub Octoverse 2025: TypeScript стал языком №1, GitHub прямо связывает это с AI. «Модели лучше работают с языками, которые раскрывают информацию о корректности, например через систему типов». [GitHub Blog](https://github.blog/ai-and-ml/llms/why-ai-is-pushing-developers-toward-typed-languages/)
3. **Быстрая обратная связь от компилятора.** Google Developers Blog: статическая типизация Go — «автоматическая страховочная сетка для агентного кода», а выдуманное поле структуры отвергается сразу. Плюс быстрая компиляция, gofmt и «один способ сделать». [Google Developers Blog](https://developers.googleblog.com/why-go-is-an-ideal-language-for-ai-assisted-software-engineering/), [Bruin](https://getbruin.com/blog/go-is-the-best-language-for-agents/), [HN](https://news.ycombinator.com/item?id=47222270)
4. **Устаревшие API в популярных Python-библиотеках.** Модели используют устаревшие API в 25–38% случаев на 8 библиотеках (ICSE 2025). Только 42,6% примеров кода исполняются в целевой версии библиотеки (2026). Для Go это смягчает гарантия совместимости Go 1, но это наш вывод, а не цифра из исследований. [arXiv 2406.09834](https://arxiv.org/abs/2406.09834), [arXiv 2604.09515](https://arxiv.org/abs/2604.09515)
5. **Выдуманные пакеты (slopsquatting).** 19,7% пакетов, которые рекомендуют модели, не существуют (USENIX Security 2025, Python и JS). Данные по Python противоречивы: 15,8% против JS 21,3% в одном исследовании и 23,1% против 14,7% в другом. Go в этих исследованиях не измерялся, но модули Go импортируются по полному URL репозитория и сверяются с go.sum. [USENIX](https://www.usenix.org/system/files/conference/usenixsecurity25/sec25cycle1-prepub-742-spracklen.pdf), [arXiv 2501.19012](https://arxiv.org/abs/2501.19012)
6. **Эксплуатация.** Единый статический бинарник без зависимостей (Google Blog). В нашем эксперименте образ 16 МБ против 255 МБ.

### Слабые места Go для агентов
- **Гонки данных.** У людей 41% гонок — захват переменной по ссылке в горутине (Uber, PLDI 2022). Компилятор их не ловит, а модели плохо находят такие гонки. Исследований именно по коду от LLM не найдено. [arXiv 2204.00764](https://arxiv.org/abs/2204.00764), [Dr.Fix arXiv 2504.15637](https://arxiv.org/abs/2504.15637)
- **Многословность.** Больше кода и больше токенов. Наш эксперимент: на 27% больше кода и на 43% больше токенов.

### Сверка с нашим экспериментом
- Python потратил меньше токенов (21,6 против 30,9 млн). Это согласуется с Tokenmaxxing и llms-token-perf.
- Go закончил быстрее, а оценки почти равны (8,0 против 7,8). На 2026 год разрыв из Multi-SWE-bench (модели 2024–25) для сильной модели не подтвердился, но у нас n = 1.
- Баги ревьюеры нашли в обеих реализациях, но разного класса. В Python это ошибки при выполнении на граничном вводе (500), типичные для динамического языка. В Go это логическая ошибка лимита курсора, которую типы не ловят.
