| Запрос | Время | План |
|---|---:|---|
| `title=zzqx` (нет совпадений), сортировка по умолчанию `-created_at` | **991 мс** | Merge Append по 64 × `books_created_idx` Backward, весь индекс отфильтрован |
| `title=zzqx&sort=title` | **1138 мс** | 64 × `books_title_idx`, примерно по 15.5 тыс. строк отброшено фильтром в каждой партиции, то есть весь индекс |
| `publisher=No Such Press&sort=title` | 238 мс | полный проход `books_title_idx` |
| `publisher=No Such Press` (по умолчанию) | 108 мс | полный проход `books_created_idx` |

После проверки: `docker compose --profile seed --profile test --profile tools down` выполнен. Volumes не трогал. В volume `lib_rust_pgdata` остались служебные БД `wl_test_*` от моего прогона llvm-cov; тестовый harness удаляет их при следующем запуске.

## 3. Топ-5 проблем по критичности

1. **Фильтр без подходящего индекса + сортировка = полный проход индекса сортировки.** `query.rs:404-432`, индексы `migrations/..._init.sql:109-117`. Сценарий: `GET /books?title=<редкая подстрока>` (даже с сортировкой по умолчанию) или `publisher=<редкий>&sort=title`. Планировщик выбирает Merge Append по `books_created_idx`/`books_title_idx` и фильтрует строки по одной. На 1 млн это 1 с, на 10 млрд гарантированный timeout и 503. Нет ни лимита на прочитанные строки, ни фоллбэка «bitmap по фильтру + top-N sort», ни запрета сортировки для неселективных комбинаций. EXPLAIN-гейт этого не видит, потому что берёт существующие значения.
2. **Фильтр `author` при частой подстроке делает Seq Scan по всему `author_books`.** `query.rs:321-336`. На 1 млн custom-план превращает LATERAL в Parallel Hash Join с Seq Scan по 64 партициям, это 119 мс. При десятках миллиардов связей это полный скан. Плюс DISTINCT и сортировка всех книг всех подходящих авторов. Автор признаёт ограничение в ARCHITECTURE §8, но ничем не защищается: нет ни cap на число авторов-кандидатов, ни минимальной селективности.
3. **Баг: 500 при keyset по `birth_date` с датами до н. э.** Автор с `birth_date: "-0427-01-01"` проходит валидацию. `query.rs:530` кладёт в курсор `"-0427-01-01"` (формат chrono), `query.rs:583-588` проверяет его через chrono и биндит строкой с `::date`. PostgreSQL отвечает `time zone displacement out of range: "-0427-01-01"`, клиент получает 500 на второй странице `GET /authors?sort=birth_date&limit=1`. Воспроизведено. Схема при этом явно разрешает даты от 3000 BC (`init.sql:34`).
4. **Масштаб партиционирования и scatter-gather.** 64 HASH-партиции дают около 156 млн строк в партиции при 10 млрд: VACUUM и перестройка индекса занимают часы, а число партиций зашито в миграции (`init.sql:104`). Любая страница списка с сортировкой — Merge Append по 64 (при шардинге по всем шардам) индексам. Около 8 индексов на `books`, из них 3 GIN, дают сильную write amplification: замер около 610 байт на строку с индексами, то есть порядка 6 ТБ только на books. `audit_log` history (`repository.rs:359`, индекс `init.sql:182`) без ограничения по `changed_at` пробует индекс в каждой месячной партиции. FK `book_authors → authors/books` (`init.sql:165-166`) несовместимы с распределением по разным ключам в Citus.
5. **Эксплуатационные риски id и аудита.** `NODE_ID` по умолчанию 1 (`docker-compose.yml:50`): при `docker compose up --scale app=N` snowflake-id и PK будут коллидировать, нет ни выдачи node-id, ни проверки. Партиции `audit_log` создаются только при migrate и старте (`db.rs:84`, `lib.rs:47`) и без DEFAULT-партиции. Если миграции не перезапускать дольше горизонта, все записи начнут падать. Ещё курсор не привязан к фильтрам: смена фильтра с тем же курсором молча продолжает с чужой позиции без 400.

Мелочи: в diff удаления `"new": "now"` вместо времени; дубликаты query-параметров берутся по принципу last-wins; для write-операций в openapi нет 503/504; `isbn_registry` не связан FK с books, и согласованность держится только на приложении (как и `author_books`, это признано в документации).

## 4. Сильные стороны

- Продуманная модель связей «в обе стороны»: `book_authors` по book_id и `author_books` по author_id. Обе выборки, «авторы книги» и «книги автора», идут в одну партицию; тест проверяет согласованность зеркал.
- Корректное решение глобальной уникальности ISBN на партиционированной таблице: `isbn_registry` партиционирована HASH по isbn_13. Гонка вставок проверена: 1×201 и 11×409. ISBN освобождается при смене и soft delete.
- Аккуратный keyset: NULL через sentinel в индексном выражении (`coalesce(year, 32767)`, `'infinity'`), row-comparison `(expr, id) > ($1,$2)`, курсор привязан к сортировке и направлению, id в JSON передаются строкой (безопасно для JS). Ранг в поиске сериализуется в курсор без потери точности (float_roundtrip, есть тест).
- Совместимость с PgBouncer: `set_config(..., true)` в каждой транзакции, read-only транзакции на чтение. Есть осознанный разбор generic и custom планов, и EXPLAIN-гейт проверяет оба.
- Сильный seed: детерминированный, по чанкам, параллельный COPY. DDL снимается и восстанавливается через `ON ONLY` + `ATTACH PARTITION`, данные многоязычные, ISBN валидные, распределение с длинным хвостом.
- Высокое качество тестов (93.9% строк, реальный PG, отдельная БД на прогон) и чистые линтеры. Образ 40 MB, distroless, non-root.
- Честная документация ограничений в ARCHITECTURE §8: часть найденных мной проблем (author-фильтр, cap поиска, фиксированное число партиций) автор признаёт сам.
