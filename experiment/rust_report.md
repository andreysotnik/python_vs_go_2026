# Финальный отчёт Rust-агента

Все пункты приёмки выполнены, финальный прогон с нуля зелёный (`docker compose down -v` → `up --build` → `make seed` → `make test` → `make explain` → `make bench` → `make lint` → `make down`). Compose остановлен, тома `lib_rust_*` оставлены. Чужие контейнеры не трогал, коммитов нет.

**1. Критерии приёмки**
- ✅ `docker compose up --build` + `make seed` + `make test` проходят после удаления своих томов. `make test` гоняет `cargo test` в контейнере `rust:1.100` против compose-PostgreSQL, локальный Rust для него не нужен.
- ✅ Swagger UI отдаётся по `/docs` (HTTP 200), спецификация — `/openapi.yaml` и `openapi.yaml` в репозитории. `redocly lint`: спецификация валидна, 5 стилевых предупреждений. Интеграционный тест проверяет, что каждая операция из спецификации действительно есть в роутере. В браузере страницу визуально не открывал.
- ✅ OFFSET нигде нет, только keyset. Seq Scan по books/authors и связанным большим таблицам нет на засеянной БД: 29 ключевых запросов проверены и в обычном плане (`EXPLAIN ANALYZE`), и в обобщённом (`EXPLAIN (GENERIC_PLAN)`), результат PASS, отчёт в `docs/QUERY_PLANS.md`.
- ✅ У каждой книги и автора есть `created_at`/`created_by`/`updated_at`/`updated_by` (с именем пользователя), `version`/ETag и soft delete. История доступна через `/books/{id}/history` и `/authors/{id}/history` (действие, кто, когда, diff по полям) и остаётся после удаления.

**2. Тесты**
- `make test`: 57 unit + 14 интеграционных API + 1 end-to-end (seed + explain) = **72 passed, 0 failed**.
- Покрытие (`cargo llvm-cov`): **93.9% строк** всего; service 94.9%, query 99.7%, validation 96.4%, repository 100%.
- `cargo fmt --check` и `clippy -D warnings` чистые.

**3. Seed и нагрузка**
- Seed 1M книг / 200k авторов / 1k пользователей, всего 5.87M строк по всем таблицам: **33.0 с**.
  - COPY-фаза 8.0 с, **732k rows/s** (книги 166k/s).
  - Пересборка индексов и FK 9.1 с, VACUUM ANALYZE 15.6 с.
  - В пересчёте на всё время: 178k rows/s.
- k6, 32 VU, 60 с, смешанная нагрузка с ~3% записей: **658 req/s, 0% ошибок**, всего **p50 36 / p95 160 / p99 260 мс**.

**4. Итерации и главные проблемы**
- Unit-тесты — 1 запуск. Интеграционные — 5: дубли snowflake-id у параллельных тестовых приложений с одним `NODE_ID`, кодирование URI, две ошибки в ожиданиях тестов.
- Docker — 2: директива `# syntax` не скачивалась (TLS timeout), и в образ попадал пустой `main` из слоя кеша зависимостей — приложение молча завершалось с кодом 0.
- EXPLAIN: запрос `language=ja&sort=title` шёл 762 мс → добавил индекс `(language_code, title, id)` → 2 мс.
- Главное: обобщённые планы (prepared statements после 5 выполнений). Обычный EXPLAIN их не видит. Под нагрузкой запрос подгрузки авторов (`= ANY($1)`) хешировал всю таблицу authors через Seq Scan.
  - Принудительные custom-планы стоили ~4 мс планирования на запрос (64 партиции), отказался от них.
  - Переписал этот запрос и фильтр по имени автора на LATERAL-поиск по PK; проверку обобщённых планов добавил в explain.
- Поиск съедал ~90% CPU базы. Ввёл два режима: полнотекстовый с переранжированием лучших 1000 и нечёткий — только если полнотекстовый ничего не нашёл. Пропускная способность 215 → 658 req/s.
- Seed был недетерминирован: диапазон дат зависел от `now`. Исправлено, тест сравнивает md5 после повторного засева.

**5. Что не сделано или упрощено**
- Аутентификация — доверенный заголовок `X-User-Id` в middleware. JWT и роли не реализованы.
- Поиск возвращает не больше 1000 результатов на тип. Нет морфологии, CJK не сегментируется (подстроки находятся через триграммы). Это самый медленный эндпоинт.
- Партиций 64/32, а не 256 (для 10B предлагаю 256, описано в `ARCHITECTURE.md`). Шардинг и OpenSearch только описаны, не реализованы.
- Двусторонние связи книга↔автор поддерживаются кодом приложения в одной транзакции, а не триггером. Задачи сверки нет, есть только тест на согласованность.
- Swagger UI грузит ассеты с unpkg — браузеру нужен интернет.
- Фильтр `author` по широкому имени тянет все книги совпавших авторов (без Seq Scan, но O(совпадений)). `total` — только оценка.
- testcontainers не использовал: тесты создают отдельную БД в compose-PostgreSQL на каждый прогон.
- Цифры нагрузки сняты на одной машине, где всё делит CPU.
