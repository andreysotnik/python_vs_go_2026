- Ручные проверки на запущенном `library serve`:
  - Optimistic locking: устаревший `If-Match` → 409, без версии → 428, версия в теле работает, DELETE с устаревшим `If-Match` → 409.
  - Дубль ISBN → 409. После soft delete ISBN освобождается и снова доступен.

## 3. Топ-5 проблем по критичности

**P1 (высокая, корректность и ТЗ). Keyset-пагинация обрывается на длинных значениях сортировки.**
Сырое значение сортировки (`title`, `full_name`) кладётся в курсор как JSON и затем в base64.
Все query-параметры, включая `cursor`, режутся общей проверкой `MaxQueryLength = 256` в `internal/domain/query.go:106` (`one()`).
Лимиты `cursor.MaxLen = 4096` (`internal/cursor/cursor.go:19`) и `maxLength: 4096` в OpenAPI до этой проверки не доходят.
Воспроизведение:
- Создать 3 книги с русским названием из 87 символов (`publisher=LONGPUB`).
- `GET /books?publisher=LONGPUB&sort=title&limit=1` отдаёт `next_cursor` длиной 278 символов.
- Следующая страница → `400 cursor: is too long (max 256 characters)`.

Для авторов то же: имя из 48 CJK-символов даёт курсор 259 символов и 400.
Порог примерно 80 кириллических, 45 CJK или 170 латинских символов. В мировом каталоге такие названия обычны: обход списка по `sort=title` просто прекращается на первой такой строке.
Тесты этого не ловят: в фикстурах только короткие названия.

**P2 (высокая, масштаб). `/search` и `q` с неподходящей сортировкой не масштабируются до 10 млрд.**
`internal/repository/search.go:15-27`: `ts_rank + word_similarity` считается для **каждого** кандидата, затем top-N sort.
Уже на 1 млн строк запрос `q=light` даёт 46 тыс. кандидатов и 378 мс (`docs/QUERY_PLANS.md`, кейс 35). На 10 млрд это сотни миллионов строк, и запрос гарантированно упрётся в `statement_timeout`.
`GET /books?q=<редкое слово>` (сортировка по умолчанию `-created_at`) идёт `Index Scan Backward ... Filter: search_vector @@ …` по всем 64 партициям. Для редкого терма это проход почти всего индекса.
Так же ведут себя `language=<редкий>&sort=-created_at`, `publisher=…&sort=title` и т. п.
EXPLAIN-чекер (`internal/explain/explain.go:25`) ищет только подстроку `Seq Scan`, а в кейсах взяты частые значения (`light`). Поэтому «40/40 PASS» не доказывает отсутствие полного прохода по индексу.
Для поиска нужен ограниченный набор кандидатов (`LIMIT` на этапе GIN, `ts_rank` по top-K) или вынос в OpenSearch. В доке это частично признаётся, но в коде защиты нет.

**P3 (средняя, корректность). Фильтр `author=` молча обрезается и недетерминирован между страницами.**
`internal/repository/books.go:50-51`: подзапрос `SELECT a.id FROM authors ... LIKE ... LIMIT 1000` без `ORDER BY`.
- Если совпало больше 1000 авторов (например, `author=ivan`), часть книг теряется без какого-либо сигнала клиенту.
- Набор из 1000 авторов не фиксирован между запросами страниц (bitmap/parallel план, вставки). Значит, keyset-обход может дать пропуски.

**P4 (средняя, масштаб и шардинг). Индексный «зоопарк» и FK на партиционированных таблицах.**
- На `books` 11 индексов (`migrations/00003_indexes.sql:6-17`, `00004`): PK, 6 B-tree и 3 GIN (`genres`, `search_vector`, trigram). На 10 млрд это десятки ТБ индексов (сам README даёт 0.8 ТБ на один trigram) и сильная write amplification на каждый INSERT или UPDATE.
- `books_publisher_idx` построен без `id`, поэтому не обслуживает keyset.
- FK `author_books.book_id → books` и `book_isbns.book_id → books` (`00002_schema.sql:78-90`) связывают таблицы с разными ключами партиционирования. В Citus такие FK между неколоцированными distributed-таблицами невозможны, их придётся снимать при шардинге.
- 64 партиции на 10 млрд — это около 150 млн строк на партицию (автор сам пишет, что нужно 256–1024).
- История из `audit_log` проверяет индекс каждой месячной партиции, и стоимость `/history` растёт линейно со временем.

**P5 (низкая, мелкие несоответствия).**
- `author_id=<удалённый автор>` возвращает его книги (`books.go:55` не проверяет `authors.deleted_at`), хотя в карточке книги этот автор уже скрыт (`LoadBookAuthors`). Фильтр `author=` удалённых авторов исключает — поведение неконсистентно.
- Курсор не привязан к фильтрам: при смене фильтров со старым курсором выдаётся «продолжение» с чужой позиции без ошибки.
- `409 duplicate` раскрывает имя внутреннего ограничения (`book_isbns_p28_pkey`, `repository/store.go:68`).
- `context.Canceled` (клиент отвалился) мапится в 500 и пишется в лог как ошибка (`httpapi/problem.go:64-67`).
- `POST /api/v1/users` не требует аутентификации и не пишется в аудит.
- `sort=--title` принимается (`TrimLeft("+-")`).

## 4. Сильные стороны

- **Глобальная уникальность ISBN на партиционированной таблице** решена правильно. `book_isbns` партиционирована по самому ISBN, её PK обеспечивает уникальность. ISBN атомарно занимается и освобождается в той же транзакции при создании, смене ISBN и soft delete. Проверено вручную: дубль → 409, после удаления ISBN снова свободен.
- **Связь книга↔автор в обе стороны**: `book_authors` по `book_id` колоцирован с `books`, зеркало `author_books` по `author_id` пишется в той же транзакции. `/authors/{id}/books` читает одну партицию.
- **Keyset сделан аккуратно**:
  - строковое сравнение `(col, id) > (?, ?)`;
  - NULLS LAST в обоих направлениях через две фазы (`keyset.go:108-118`), фаза NULL тоже обслуживается индексом `(col, id)`;
  - курсор привязан к сортировке;
  - точный round-trip `float64` для rank;
  - OFFSET нигде не генерируется.
- **Total** берётся из оценки `EXPLAIN (FORMAT JSON)`, а не `COUNT(*)`, и только по запросу.
- **Optimistic locking** двухуровневый (`SELECT … FOR UPDATE` + `UPDATE … WHERE version=$n`). Поддержаны `If-Match`/`ETag` и версия в теле; без версии → 428.
- **Аудит**: field-level diff `{old,new}` в той же транзакции, история доступна и для удалённых сущностей.
- **Seed**: COPY параллельными пачками, снятие и восстановление вторичных индексов и FK с бэкапом DDL на случай краха, исправление `ON ONLY` у `pg_get_indexdef` для партиционированных таблиц, `VACUUM ANALYZE`, детерминированность.
- **Строгая валидация**: неизвестные query-параметры и поля тела → 400, проверка ISBN с контрольной цифрой и совпадения ISBN-10/13, CHECK-ограничения в БД.
- **Эксплуатация**: образ около 15 МБ на distroless nonroot, healthcheck без shell, приватный Prometheus registry, request_id, JSON-логи, `statement_timeout` startup-параметром, режим PgBouncer (`QueryExecModeExec`).
- **Документация** (ARCHITECTURE, README) честно описывает ограничения, путь к Citus и OpenSearch (outbox/CDC) и экстраполяцию на 10 млрд.
